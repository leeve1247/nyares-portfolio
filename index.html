3. AI 활용 사례

세 사례 모두 같은 순서로 적었습니다. 문제, AI에게 맡긴 일, 내가 판단·검증한 일, 결과.

사례 1. "최적화해야 한다"는 말을 측정으로 바꾸기2026년 11월 22~23일

문제

11월 22일 회의에서 "이제 최적화도 해야 한다"는 말이 나왔습니다. 비슷한 말이 10월 16일, 10월 31일, 11월 13일 회의에도 있었습니다. 코드 대부분을 AI가 쓰기 때문에 어디가 느린지 사람이 코드를 읽어서는 알기 어렵고, 느낌만으로 고치기 시작하면 어디까지 고칠지 정할 수 없습니다.

AI에게 맡긴 일
  • 측정. 데모의 14개 화면을 같은 조건으로 띄우고 화면마다 연속 150프레임을 Unity 프로파일러로 기록해 집계
  • 수정. 측정에서 찾은 낭비 다섯 군데를 고침. 화면이 가만히 있어도 매 프레임 버튼 위치를 다시 계산하고 문자열을 새로 만들던 코드
  • 확인. 같은 문제가 다시 생기면 실패하는 테스트 2개를 작성하고, 수정 전후 10개 화면을 같은 설정으로 찍어 픽셀 단위로 비교
  • 정리. 결과를 화면별 수치 표와 문서로 만들고, 실제 게임에서 문제가 되는 수준인지 판단할 근거를 제시

측정, 분석, 수정은 거의 전부 AI가 했습니다.

내가 판단·검증한 일
  • "최적화해 줘"라고 시키지 않았습니다. "실제 게임에서 문제가 되는지 판단할 수 있게 해 달라"고 요청했습니다.
  • 결과를 제가 읽을 수 있는 형태로 바꿔 달라고 했습니다. 프로파일러 원본 대신 화면별 수치 표와 결론을 받았습니다.

제가 한 일은 이 두 가지입니다. 아래 결론과 고칠 곳은 AI의 측정에서 나왔습니다.

결과

결론은 "지금 데모에 프레임을 떨어뜨리는 병목은 없다"였습니다. 14개 화면의 프레임 시간 중앙값이 1.5~6.8ms로, 60fps 기준인 16.7ms 안입니다. 수정으로 줄어든 것은 프레임당 메모리 할당입니다. 아래는 14개 화면 중 세 곳입니다.

초원 전투18,518 B2,766 B
심장 제단19,828 B236 B

Unity 에디터에서 잰 값이고, 수정 전 값에는 에디터에서만 생기는 할당이 일부 섞여 있습니다. 프레임 시간 차이는 측정 오차 안입니다. 측정은 모두 macOS에서 했고 Windows와 저사양 PC는 재지 못했습니다.

이어서 화면이 바뀔 때 한 프레임에 몰려 있던 화면 생성 작업을 여러 프레임에 나눴습니다. 전투 전 배치 화면으로 넘어갈 때 가장 긴 프레임이 535~900ms에서 317~360ms로 줄었습니다. 전환에 걸리는 전체 시간은 줄지 않았습니다.

사례 2. 데모를 업데이트해도 하던 원정을 이어 가게 하기2026년 11월 22일

문제

데모를 0.3.1에서 0.3.2로 올리자, 0.3.1에서 진행하던 원정(한 판의 진행 상태)을 0.3.2에서 이어 할 수 없었습니다. 원인은 저장 파일에 적어 두는 호환 확인 값이었습니다. 병사 편성과 수치 데이터 전체의 해시(내용이 조금만 달라도 바뀌는 값)를 쓰고 있어서, 공격력 숫자나 번역 문구만 고쳐도 이전 저장이 전부 거부됐습니다. 데모를 업데이트할 때마다 플레이어의 진행이 끊길 수 있는 기준이었습니다.

AI에게 맡긴 일
  • 0.3.1 저장이 거부되는 경로를 찾아 수정
  • 호환 테스트 작성. 완료 조건은 "이전 버전에서 저장한 원정을 새 빌드에서 이어 갈 수 있다"로 전달

구체적인 구현과 테스트 코드는 AI가 작성했습니다.

내가 판단·검증한 일
  • 0.3.1 저장을 허용하는 수정에서 끝내지 않고 기준을 바꾸기로 했습니다. 배포할 때마다 바뀌는 해시 대신, 저장 형식이 달라질 때만 사람이 올리는 호환 버전을 저장 파일에 적게 했습니다. 수치나 번역이 바뀌어도 이어 할 수 있습니다.
  • 이미 배포한 0.3.1과 0.3.2의 저장도 계속 받기로 했습니다. 두 버전이 Windows와 macOS에서 기록한 해시 4개를 목록에 넣어 첫 호환 버전과 같게 취급합니다.
  • 테스트가 두 방향을 모두 확인하는지 봤습니다. 이전 해시 4개로 저장한 원정은 복원되고, 모르는 버전이나 빈 값은 거부되어야 합니다.
결과

0.3.1 저장을 허용하는 수정과 기준 변경을 같은 날 따로 합쳤습니다. 0.3.1에서 하던 원정을 0.3.2에서 이어 할 수 있고, 이후 배포에서는 저장 형식을 바꾸지 않는 한 호환을 위해 따로 할 일이 없습니다. 그래도 이어 할 수 없는 저장은 지우지 않고 보관한 뒤 한 번만 알려 줍니다(11월 16일에 넣은 처리).

사례 3. 기획 의견이 갈릴 때 각자 AI로 시제품을 만들어 비교하기2026년 11월 23일

문제

플레이어가 잘 쓰지 않는 병사를 다시 쓰게 만드는 근본적인 해결책을 찾는 회의였습니다. 레벨이 높은 병사와 낮은 병사를 묶어 주자는 데까지는 의견이 모였습니다. 묶는 방식에서 제 안과 팀원 두 명의 안이 갈렸고, 말로는 결론이 나지 않았습니다.

AI에게 맡긴 일
  • 아이디어 넓히기. 후보를 좁히기 전, 방안을 여럿 펼쳐 보는 단계에서만 AI를 썼습니다. 회의 중 공유 문서에 후보 16개가 모였습니다.
  • 시제품 구현. 두 안을 각자 AI로 완성본에 가깝게 만듭니다.
내가 판단·검증한 일
  • 후보 16개는 AI 없이 팀 투표로 3개로 줄였습니다. 재미있어 보여도 이미 복잡한 시스템을 더 어렵게 만드는 후보는 논의에서 빠졌습니다.
  • 묶는 방식은 더 논의하지 않고 시제품으로 고르자고 제안했고, 팀이 동의했습니다. AI로 만드는 비용이 낮아져 회의를 한 번 더 하는 것보다 만들어 보는 편이 빠르다고 판단했습니다.
  • 비교할 상황을 미리 정했습니다. 병사가 꽤 모인 중후반에 레벨이 높은 병사 하나가 거의 쓰러진 상황을 두 시제품에서 똑같이 만들어 플레이합니다. 어느 안을 넣을지는 AI의 평가가 아니라 팀원이 해 본 결과로 정합니다.
결과

11월 24일 기준으로 시제품은 만들어 둔 상태이고, 팀이 함께 해 보고 고르는 일은 아직 남아 있습니다.

4. 작업 방식

다른 사람이 같은 방식으로 일할 수 있게 순서대로 적습니다. 도구는 Claude와 Codex 데스크톱 앱입니다.

  1. 기록을 저장소에 모읍니다. 회의 녹음을 정리한 회의록이 저장소에 자동으로 올라오고(봇이 올린 변경 80건), 결정 사항은 저장소 안의 LLM 위키에 반영됩니다. LLM 위키는 AI와 사람이 함께 읽는 프로젝트 문서 모음입니다.
  2. 역기획서로 현재 상태를 확인합니다. 역기획서는 기획 의도가 아니라 실제 빌드가 어떻게 동작하는지를 측정해 적은 문서입니다. 정한 것(위키)과 구현된 것(역기획서)을 대조하고, 어긋난 곳은 따로 목록으로 관리합니다.
  3. 무엇을 만들지는 사람이 정합니다. 팀 회의나 혼자 숙고하는 시간을 거쳐 결정합니다.
  4. 작업 하나에 AI 세션 하나를 엽니다. 세션마다 작업 보고를 받고, 보고를 보며 방향을 고쳐 지시합니다.
  5. 끝난 작업은 둘로 나눕니다. 팀 결정이 필요한 것은 브랜치에 남겨 회의에서 보여 주고, 결정이 끝난 것은 바로 메인 브랜치에 합칩니다. 메인 브랜치 하나와 수명이 짧은 작업 브랜치만 두는 트렁크 기반 개발입니다. 메인에 직접 올리는 것은 막아 두었고, 모든 변경은 AI 자동 리뷰를 거친 뒤 한 건으로 합쳐집니다.
  6. 작업 규칙은 AGENTS.md 한 파일에 둡니다. 저장소에 두는 AI용 작업 지침입니다. Claude와 Codex, 자동 리뷰 봇이 같은 파일을 읽습니다. 예를 들어 "짧은 지시를 받아도 정해진 작업 절차를 생략하지 않는다", "플레이어에게 보이는 한국어 문구를 고치면 영어·일본어 번역도 함께 넣는다", "순서를 틀리면 복구가 비싼 작업은 절차 문서를 먼저 읽는다" 같은 규칙이 있습니다.

6. 그 외 프로젝트

커뮤니티 서비스 클론 (개인 프로젝트, 2024년 8월 ~ 2025년 12월, 운영하지 않음). 백엔드 서버 개발을 공부하며 혼자 만들었습니다. Spring Boot와 JPA로 게시글·댓글·좋아요 API를 구현하고, 조회수 갱신을 Redis에 모아 처리했으며, 쓰이지 않는 첨부 이미지를 스케줄러로 정리했습니다. OIDC 인증 서버와 Keycloak용 네이버 로그인 확장을 구현했습니다. 프런트엔드는 React로 만들었고 전체를 Docker Compose로 구성했습니다.
